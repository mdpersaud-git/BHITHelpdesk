# Branthaven IT Help Desk – Technician Guide

Site: https://branthavenhomes.sharepoint.com/sites/ITHelpDeskv2
Business day for SLA purposes: the hourly clock (HD6, and the BusinessHoursOpen/SLAHours it writes) runs **8am–9pm**, every day. Response-time credit ("Response (min)") is more generous — it counts from 7am (support opens) regardless of when the ticket was actually raised; see the note under "Service levels" below.

## How tickets arrive

| Source | What happens |
|---|---|
| Email to the help desk mailbox | HD1 creates a ticket. A reply containing an [IT-123] tag updates that ticket. Branthaven senders always get a ticket; outside senders only if their address or domain is on the **External Senders** list (see below). Everything else lands in the mailbox's **Review** folder and is ignored — except a Microsoft Teams "missed activity" relay (someone messaged IT Support's own Teams presence and it went unread), which still can't become a ticket but now also alerts Martin by email and Teams before parking in Review (see "Review folder" below). |
| IT Support form (Microsoft Forms) | HD2 creates a ticket. |
| **Report an IT issue** Teams app | HD14 creates a ticket (source: "Teams form"). |

Every new ticket then runs HD3: it sets permissions (the requester sees only their own ticket), creates the **Planner task**, emails and messages the requester a confirmation (as IT Support), alerts IT in the Help Desk channel, and sends Martin and Joseph a direct Teams message from IT Support with the ticket number, requester, priority and link.

Every HD4 run (any note, status change, or resolution) also rewrites the Planner task's own **Notes** to the ticket title, a link, and the ticket's conversation history (capped at ~1800 characters) — so a tech reading the task in Planner sees the same notes and resolution text as the ticket itself, without opening SharePoint. It's a full rebuild each time, not an append, so nothing you type directly into the Planner task's notes will survive the next ticket update — put any notes on the ticket (Edit ticket / note box) instead.

**Attaching a file to a ticket:** attaching it doesn't notify the requester by itself — attaching a file doesn't change Status, IT Assigned, or Note to requester, and only those trigger HD4. Put a line in **Note to requester** (even just "see attached file") so HD4 fires. When it does, HD4 checks the ticket's attachments fresh each run and, if any haven't been linked before, adds a direct download link for each one right in the email and Teams message — the requester doesn't need to open the ticket just to find the file.

Only *new* attachments get linked, not every file ever added to the ticket — a **NotifiedAttachments0** field (pipe-separated filenames, kept off every form and view) tracks what's already gone out, so the requester's own originally-submitted file doesn't get re-linked on every later update. It only advances when a note/status notification actually sends — a reassignment-only edit with no note won't mark a pending file as "seen." (It's `NotifiedAttachments0`, not `NotifiedAttachments` — see `CLAUDE.md` for why.)

The one exception: the status email/Teams message sent when a ticket reaches **Resolved Pending Confirmation** or **Closed** lists *every* attachment on the ticket — whatever the requester originally sent plus whatever a tech added along the way — not just the ones not yet linked, since that's the message most likely to get kept or forwarded. Every other note or status change still only links new files.

## Your daily workflow

1. Watch the **Help Desk channel** and the **Planner board** (buckets: New, In progress, Waiting, Done).
2. **Claim a ticket**: on the card, **Start work** if you are starting now (assigns it to you and sets *In Progress* in one update — one message to the requester), or **Assign to me** if you will get to it later (status *Assigned*; use Start work when you begin).
3. **Work it**: keep Status accurate – it drives the SLA clock, the Planner bucket and the messages the requester receives.
4. **Change priority, category or who it's assigned to**: use **Edit ticket** on the card. Pick only what you want to change and leave the rest on *(keep current)*. Reassigning notifies the new technician and the requester; priority/category changes are noted in the card's thread.
5. **Fixed it on the spot?** Use **Quick close** on the card: type the resolution, Send. The ticket is assigned to you and closed in one step and the requester gets one message ("Resolved" with your resolution) instead of three or four. Use it for walk-ups, phone fixes and password resets; for anything the user needs to try first, use Resolved Pending Confirmation instead. The same button exists in the **SharePoint list** (the ✓ icon next to the ticket number, hidden once a ticket is Closed): SharePoint asks for the resolution, then HD18 assigns the ticket to you (unless it already has a tech) and closes it in one update — the requester gets the same single "Resolved" message. The other icons in that column are Edit, Assign to me and Start work; their definition is `dashboard/tickets-id-column.json` (change it there, then paste into the ID column's Format this column, never only in SharePoint). HD18 must list every tech under **Run-only users** (flow details page), with both connections set to *Use this connection (IT_Support)* — otherwise the button shows "cannot be used to activate this flow". Add new techs there when they join. SharePoint always shows a confirm panel with a **Run flow** button before a column-button flow actually runs (same as Microsoft's own native "Flow" command — there's no way to skip it or make it submit on Enter); HD18's flow **Description** (Power Automate → flow → Details → Edit) is set to a one-line reminder to click Run flow, which SharePoint shows under the owner line in that panel — change it there (never only on a copy of the flow) if the wording needs updating.
   If you resolve or close a ticket by editing it directly and forget to assign it, HD4 assigns it to you (the editor) before sending anything, so the requester's email never says "Not yet assigned" for a ticket a tech just fixed.
   Quick close (Teams or SharePoint) assigns and closes the ticket in one update, so HD4 would normally both assign you in Planner (a Planner "assigned to you" notification) and mark the task complete in that same run; since Oct 2026 HD4 skips the Planner assignment step whenever the ticket is landing on Resolved/Closed in the same update, so Quick close no longer generates an assignment notification for a task that's already done — the Planner task still moves to the Done bucket and 100%. A tech assigned to a ticket that stays open (not via Quick close) still gets the normal Planner assignment notification.
6. **Ask the requester a question**: use the card/reply action on the ticket thread in Teams. The question reaches them as an IT Support message and their answer (by Teams or email) is posted back on the ticket.
7. **Resolve**: set Status to *Resolved Pending Confirmation* (or complete the Planner task), with a resolution written in the message box. The requester is notified, including your resolution text.
8. The system **closes it automatically after 48 hours**, with a reminder to the requester at 24 hours; the automatic close itself is silent (the resolved email already told them it would happen). Set *Closed* yourself if they confirm earlier — **a resolution is required to close a ticket**: if none was captured yet (e.g. closing directly without going through Resolved Pending Confirmation), enter it in the message box when you set Status to Closed, or the flow will bounce it back to you and leave the ticket open. This is enforced three ways: the Teams card blocks it outright, if a ticket is set to Closed by any other means (e.g. editing the list item directly) with no resolution on file HD4 reverts it to its prior status and messages you to add one, and completing the ticket's **Planner task** only moves the ticket to Resolved Pending Confirmation if a resolution is already on file — otherwise HD5 reopens the task and messages you to add the resolution first.

## Logging a ticket for someone else

In the **Report an IT issue** app, fill in **On behalf of** with the person's Branthaven email address (e.g. jane@branthaven.com). The ticket then belongs to that person: they get the confirmation and every update, and the ticket shows *Logged by <you>*. It is **not** assigned to you. It lands unassigned like any other ticket, so the team can pick it up. Leave the box empty to log a ticket for yourself. Only @branthaven.com addresses are accepted.

## External senders (vendors, trades, consultants)

Outside addresses can raise and work tickets **by email only**. Add them to the **External Senders** list on the help desk site: one row per entry, **Title** = either a whole domain (`acmeplumbing.ca`) or one address (`bob.smith@gmail.com`); case doesn't matter. Remove the row to cut them off. Changes take effect on the next email — no flow change needed.

What's different for an external ticket:

- The Conversation log starts with "Ticket created from Email (external sender)". The Requester person field is empty; **Requester Email** holds their address.
- They get the same confirmation, status and reminder **emails**, without the View-ticket / portal links — they have no access to the site. They never get Teams messages.
- They reply by email (keeping IT-<n> in the subject) and that's posted to the ticket exactly like an internal reply. Techs work the ticket the same way.
- Anything from an address that isn't on the list stays in the **Review** folder. Glance at it now and then; a legitimate request from an unknown vendor means "add them to the list and forward the email to the mailbox", not a manual ticket.

### Review folder — Teams missed-activity relays now alert you

If someone messages the IT Support Teams presence directly (not a channel, not a chat reply HD12 already catches) and it goes unread, Microsoft Teams emails the mailbox a "**<name> sent a message**" / "**<name> is trying to reach you in Microsoft Teams**" notification. The sender on these is always Microsoft's own relay address (contains `teams.mail.microsoft`), never the actual person — so it can never be on the External Senders list and can never become a real ticket (no reliable requester identity). Since 2026-10-26, HD1 recognizes these specifically: it still can't ticket them, but it now relays the content to Martin by email and Teams (`[Help desk health] Missed Teams message: <subject>`) before moving the original to Review, the same pattern HD1 already uses for Power Automate's own system alerts. Before that fix, these were indistinguishable from random unknown-sender spam and simply disappeared into Review with zero alerting — see the troubleshooting table.

## Status guide

| Status | Use when | SLA clock |
|---|---|---|
| Open | New, unassigned | Running |
| Assigned | Given to a tech | Running |
| In Progress | You are working it | Running |
| Escalated or Waiting Internally | Waiting on another internal team | Running |
| Waiting for End User | You need info from the requester | Paused |
| To Be Scheduled | Booking a time with the requester | Paused |
| Resolved Pending Confirmation | Fix delivered, awaiting confirmation | Stopped |
| Closed | Finished (requesters see this status as **Resolved** in their emails and Teams messages) | Stopped |

Status changes automatically notify the requester (email + Teams) and move the Planner card.

## Per-tech service levels

The **By IT Support (30 days)** view of the Tickets list groups the last 30 days of tickets by technician. Each ticket shows **Response (min)** (from the ticket's effective start — 7am for anything raised outside 7am–9pm — to the first IT action), **Response met** (within 4 h) and **Resolved in 24 h** (24 SLA-clock hours). The totals row under each group gives that tech's averages; the bottom row is the team. The same numbers, laid out properly, are on the **IT Dashboard → Service levels by technician** panel (HD15, refreshed every 5 minutes). HD4 writes the three figures once per ticket; they are never recalculated, so a reassignment does not move the credit.

Every full business day it stays open after that (24h, 48h, ...) sends a "still open" reminder, Teams and email — while it's still unassigned, that goes to Martin and Joseph (same audience as the 5-hour ping, just repeating daily); once a tech is assigned, it goes to that tech alone (email added 2026-10-27, same day as the rest of this line — only the 4h channel post stays Teams/channel-only, as it always was).
  Since 2026-10-27 (per Martin's request), the assigned tech (or Martin, if a ticket is somehow still unassigned when one of these fires) is also pinged by **Teams and email** whenever a requester-facing wait/resolution notification goes out: the daily "still waiting on you" reminder and the 5-day no-reply auto-close for **Waiting for End User**, and the 24h "is it fixed?" reminder and the 48h no-reply auto-close for **Resolved Pending Confirmation**.
- **HD8 (9am daily, moved from 9pm 2026-10-29):** daily report of overdue tickets (open longer than a business day) and unassigned tickets (4+ hours), emailed to Martin and Joseph (Joseph added 2026-10-29). The report-building helpers (`rpt_tile`/`rpt_card`/`rpt_th`/`rpt_td`/`rpt_rowx`/`rpt_listbody`/`rpt_bar`/`rpt_wrap` in `generator/gen.py`) are shared with HD23 below, so a future daily/monthly restyle only needs changing one place.
- **HD23 (1st of the month, 9am):** a cumulative monthly rollup for the month that just ended — tickets opened, tickets closed, avg hours to close, tickets still open from that month, tickets closed by technician, and tickets opened by category — emailed to Martin and Joseph and archived to `/Reports` as `IT Support Monthly Report - <Month Year>.pdf`. Added 2026-10-29. Deliberately does **not** carry over HD8's Overdue/Unassigned/Waiting sections — those are point-in-time snapshots, not something that sums over a month — and has no self-check, same as HD21 (a scheduled sweep, not a per-item flow).
- **HD7:** a requester can ask for "My open tickets" and gets a list.

## Monitoring (is the system healthy?)

**Look first at the IT Dashboard → "System health" panel** (top of https://branthavenhomes.sharepoint.com/sites/ITHelpDeskv2/SitePages/IT-Dashboard.aspx). Eight cards, each green OK / amber CHECK / red PROBLEM / grey – (could not check), refreshed every hour at :30, around the clock, by **HD16 Health check v2**. Under the cards, one line per problem (ticket numbers only; detail is in the daily email). If HD16 itself stops, the whole panel fades and the headline pill turns grey **"STALE — health check has not run since …"** (the view compares `Slot22`, the time of the check as epoch milliseconds, with now; 90 min grace).

| Card | What it checks | Red means |
|---|---|---|
| Connections | A read-only call through every connector each hour: Outlook (mailbox), Teams (channels), Teams as IT Support (joined teams), Planner (buckets), Office 365 Users, OneDrive, Power Automate Management; SharePoint is exercised by the ticket queries. Microsoft Forms has no read action and is **not** probed. | Names the broken connection — Power Automate › Connections › Reconnect, or recreate it (see "Emails stop but Teams messages still arrive" below) |
| Flows | Power Automate Management "List My Flows": every expected flow (HD1–HD9, HD11, HD12, HD15, HD16 v2) is **on, exactly once**. | Clock & auto-close (HD6) | An open ticket has been touched in the last 3 h (checked 11:00–21:59 only, since HD6 runs 8–21); nothing resolved more than 72 h ago is still "Resolved Pending Confirmation" | HD6 stopped — SLA clock, reminders and auto-close are all off |

Problems reported by the HD3/HD4 self-checks in the last 24 h are added to the band under the cards (the step name is in the alert email). This is DASH_HEALTH's own Slot10/Slot11 — HD19/HD20's self-checks stamp DASH_PROJHEALTH's separate Slot10/Slot11 instead (see "IT Project Systems panel" below), so a project self-check problem never shows up on this (ticket) band, inflates this panel's `Total`, or trips this panel's Daily/Alert_if_changed email — and vice versa. Before 2026-10-26 `self_check()` always stamped DASH_HEALTH regardless of which flow called it, so an HD19/HD20 failure could silently overwrite a real ticket problem here (or show up mislabeled under this "HD3/HD4" band) — see the troubleshooting table.

Behind the panel, three layers of alerts all go to Martin (mpersaud@branthaven.com), each **by email and as a Teams message from IT Support**:

1. **Per-ticket/per-project, immediately.** HD3/HD4 (tickets) and HD19/HD20 (projects) check their own work at the end of every run — the named notification steps directly (confirmation email, confirmation chat, Planner task, channel post; status email, status chat, note email/chat, new-tech chat, Planner move for tickets; creation/update emails and Teams messages to creator, Martin, sponsors/owners for projects), not just the scope summaries, so a failure nested inside a condition is caught. If any did not succeed, Martin gets an email and a Teams message naming the ticket/project, the failed step, the error text and a link to the flow run. The record itself is still created/updated — only the notification is reported. This immediate alert always fires regardless of the dashboard-panel split above; only the *dashboard* stamp (and so the 24h band/Total on the panel) is routed to the matching panel.
2. **HD16 health check, hourly, 24/7.** Updates the panel every run; emails Martin a report once a day at 9:30 am (subject "[Help desk health] All clear" or "[Help desk health] PROBLEMS: n"); emails and Teams-messages him whenever the issue count changes, **between 7 am and 9 pm only** — an overnight problem waits on the panel and is in the 7:30 am run.
3. **Hard flow failures.** Power Automate emails the flow owner (the IT Support mailbox) whenever a run fails outright, when a connection breaks, and in a weekly digest. HD1 recognises those (sender @microsoft.com, subject mentioning a flow, a failure or a connection that isn't working), relays each one to Martin by email ("[Help desk health] <original subject>") and Teams, and parks the original in the Review folder.

If an alert names a flow run, open the link: the failed step is highlighted in red with the full error.

The panel's rendering is the JSON view formatting on the **Live overview** list's *Chart - Health* view (filtered to item 14). The source of truth is `dashboard/health-view.json` in the repo: paste it into the view via *Format current view → Advanced mode* whenever it changes. Column map: cards 1–7 use `Slot n` (name), `Slot n+14` (description) and `Share n` (0 OK / 50 amber / 100 red / −1 grey); `Total` = issue count, `Refreshed` = time shown, `Slot22` = time of the check in epoch ms, `Grad` = the problem band, `Slot10`/`Slot11` = last HD3/HD4 self-reported problem and its time (HD19/HD20 never write these — see "IT Project Systems panel" below). Card 8 (Reauthentication, added 2026-10-26) breaks the `n+14` pattern because `Slot22` was already taken by the epoch-ms stale timestamp above — it uses `Slot8` (name), `Slot23` (description) and `Share8` (status) instead. The **Live overview** list already has `Slot1`–`Slot30`/`Share1`–`Share30` provisioned, so adding this card needed no new SharePoint columns — only the view JSON and `generator/gen.py`.

## IT Projects (project tracking)

A separate list, **IT Projects** (same site, nav link next to Tickets), tracks longer-running work that isn't a single ticket — rollouts, infrastructure work, process changes. It has its own Status (`Not Started` / `In Progress` / `On Hold` / `Waiting on Vendor/Approval` / `Completed` / `Cancelled`) and Category (`Infrastructure` / `Security` / `Software Rollout` / `Network` / `Hardware Refresh` / `Process Improvement` / `Other`) choice columns — keep both lists in sync with `PRJ_STATUSES`/`PRJ_CATEGORIES` in `generator/gen.py` if either ever changes. "Active" for monitoring/staleness purposes means every status except Completed/Cancelled.

The list's Status and Priority columns carry the same modern colored-pill/icon styling as the Tickets list's Status and Priority columns, via **Column JSON Formatting** (not the view formatting the donuts/health panels use — this is applied per-column through a column's own *Format this column → Advanced mode*, and it's list-wide, so it shows on every view — All Items, Active Projects, Full Detail — automatically). Source of truth: `dashboard/project-status-column.json` (colored pill per Status choice, same palette family as the Tickets Status column: grey Not Started, blue In Progress, amber On Hold, purple Waiting on Vendor/Approval, green Completed, red Cancelled) and `dashboard/project-priority-column.json` (identical to the Tickets Priority column's formatting, reused verbatim since both lists share the same High/Medium/Low choices — colored icon + label). To reapply or change: open the column's dropdown → *Column settings → Format this column*, scroll down to *Advanced mode*, select all and paste the file's contents, Preview, then Save.

The list's **Title** column's display name is **"Project"** (changed 2026-10-28; internal name stays `Title`, so nothing downstream — `pt('Title')`, notification templates, `self_check`, views — needed touching). ### Multiple Owners and Project Sponsors

Both the **Owner** and **Project Sponsor** columns have **"Allow multiple selections"** turned on, so a project can list more than one tech as Owner and more than one person as Sponsor (added 2026-10-25, prompted by projects that genuinely have more than one person on either side). Mechanically:

- The SharePoint connector exposes a multi-value Person field (in a trigger body or a `GetItem`/`GetItems` result) as an **array** of objects shaped like the old single-value field — `{Email, DisplayName, Claims, ...}` — just array-wrapped, rather than one object (confirmed live against a real trigger body: `Owner.0.Email`, `Owner.1.Email`, ...). Power Automate's expression language has **no inline `select()`/`filter()` lambda** — "Select" and "Filter array" exist only as dedicated actions — so pulling `Email`/`DisplayName` out of the array needs an actual `generator/gen.py` `people_select()` **action**, with `join_emails()`/`join_names()` reading its `body(...)` afterwards to build the `;`-joined email list / comma-joined display-name list; `people_contains()` does the exact-match membership check a different way (JSON-substring match — see the troubleshooting table below) since the two places that need it have no action of their own to attach a nested Select to. `notify_each()` loops a joined email list to 1:1-message every non-empty, internal, non-duplicate address.
- **ProjectSponsor** also keeps the pre-existing plain-text **SponsorEmail** column as a fallback, used only when no Project Sponsor person is set (a manually-typed address from before the field supported people at all) — `join_emails()` takes it as a second argument and only falls back to it when the person array is empty.
- HD19 grants Read to every sponsor (looped `Ensure_sponsor`/`Give_sponsor_read`, one iteration per address) and Teams-messages every owner/sponsor individually, not just the first one.
- HD1's project-reply sender check (`prj_auth`) and HD12's `Sponsor_projects` match now do an exact-match **array** membership check (`people_contains`) against each project's Owner/ProjectSponsor array, not a single `?['Email']` lookup — anyone listed as an Owner or a Sponsor on a project (not just "the" Owner/Sponsor) can reply to add a Sponsor Updates note.
- **Live-tested clean (2026-10-25).** First live pass (creating a real 2-owner/2-sponsor test project) caught the `select()` bug above and the `InternalLine`/self-retrigger bugs in the troubleshooting table; all three fixed, `HD1.zip`/`HD12.zip`/`HD19.zip`/`HD20.zip` re-imported with **Update**, then re-run clean end to end: HD19 fired on creation (permissions broken correctly, every owner/sponsor notified individually); HD20 fired on a Status change and again on an Internal Notes-only edit, each notifying the right audience (sponsors excluded from the internal note) with no self-retrigger loop; a **PRJ-n email reply from an Owner who is not "the" (first) Owner** (`mpersaud@branthaven.com`, listed second in PRJ-4's Owner array behind `bh_support@branthaven.com`) correctly matched via HD1's array-membership `prj_auth` check (`Project found and authorized` = True), patched SponsorUpdates (PatchItem HTTP 200), and sent the sender a confirmation email; the same array-membership match was independently confirmed via **Teams** on HD12's `Sponsor_projects`/`Tagged_sponsor_project` chain (sender matched by Owner-array membership, not "the" owner), patched SponsorUpdates, and replied confirming the project. Checked every flow's run history each time, not just the one under test, per the rule above — no bug found outside the ones already listed in the troubleshooting table.

- **Teams** — HD12 is the single webhook on IT Support's chats. ### Project tasks

A separate list, **Project Tasks** (same site, not linked in the nav — opened from the project or from Site Contents), holds sub-tasks within an IT Project: `Title`, `ProjectID` (Number — the parent project's ID, not a Lookup column), `Assigned To` (Person, single selection — internal name `Assigned_x0020_To`), `Status` (Choice: Not Started / In Progress / Completed, default Not Started), `Due Date` (DateTime, date-only — internal name `Due_x0020_Date`), `Notes` (multi-line plain text), plus the bookkeeping columns `LastNotifiedStatus`/`LastNotifiedAssignee`. Added 2026-10-29. **Why a plain SharePoint list and not Planner**: Martin compared both and chose this list — simpler rollup math (count/percent across one list, no bucket-per-project to create and manage) over Planner's richer task UI.

Deliberately, the IT Projects item itself shows **only a rollup**, never the full task list — a new `Task Progress` column (internal name `Task_x0020_Progress`, plain Text, e.g. `"3 of 5 tasks complete"` or `"No tasks yet"`) patched by HD24/HD25 whenever a task is added or its Status changes. There's no task sub-grid embedded in the project's own view/form. The task's **assignee** still needs to stay on track day to day though, not just get a one-time ping — that's what HD26's daily sweep (below) is for.

Permissions: the Project Tasks list has unique permissions (does not inherit from the site) — the site Owners group gets Full Control, Talal and Joseph get Contribute (per the same rationale as Tickets/IT Projects in "Who can see a ticket (permissions)" below), granted at the **list level** (unlike Tickets/IT Projects, there's no per-item permission-breaking step on individual tasks — nothing on a task is sensitive enough to need narrower visibility than "anyone who can already see projects at all").

Three flows run it, the same `created`/`updated`/`no-update-check` pattern as HD19/HD20/HD21 for projects (and HD3/HD4/HD6 for tickets):

- **HD24 Project task created** — looks up the parent project (GetItem via `ProjectID`) for its Owner(s) and creator, then emails/Teams-messages the task's **Assigned To** person (what the task is, when it's due) and every project **Owner plus the creator** (who it's assigned to) — same "both sides" shape HD19 uses for Owner/ProjectSponsor on the project itself. Recomputes and patches `Task Progress` on the parent project. Stamps `LastNotifiedStatus`/`LastNotifiedAssignee` so HD25 has a clean baseline.
- **HD25 Project task updated** — compares Status/Assigned To against `LastNotifiedStatus`/`LastNotifiedAssignee`; a trigger-level condition (mirroring HD20's fix — see the troubleshooting table) stops the flow re-triggering forever off its own end-of-run patch. A **reassignment** (new Assigned To, not simultaneously completed) notifies the new assignee like HD24 does on creation. Moving Status to **Completed** notifies the assignee (confirmation) plus every project Owner and the creator (who finished it). Any other status change (e.g. back to In Progress) gets no notification of its own — HD26's daily sweep already keeps an unfinished task visible. Recomputes/patches `Task Progress` whenever Status changed; restamps `LastNotifiedStatus`/`LastNotifiedAssignee` either way.
- **HD26 Project task overdue check** — runs daily at 9:15am (15 minutes after HD21's 9am project sweep, so the two daily list scans don't land in the same second). Every not-Completed task that's past its Due Date, or has no Due Date and hasn't been touched in 5+ days (same no-due-date fallback HD21 uses), gets a daily nudge (email + Teams) to **both** its assignee **and** the parent project's Owner(s)/creator — looked up per task via a nested `GetItem` on `ProjectID`, since each loop iteration here is a task, not a project. Like HD21, there's no `LastNotified*` stamp and no change-detection — the filter and cadence are both unconditional, so an overdue task is re-nudged every day until it's completed or its Due Date/Modified moves it out of the filter. No self-check, same as HD21/HD23 (a scheduled sweep, not a per-item flow).

**The 5-day "stale" threshold for a task with no Due Date set is an assumption**, chosen to match HD21's existing no-update-check window for projects, not something Martin specified — revisit if a shorter/longer grace period turns out to fit how tasks are actually used.

HD24/HD25/HD26 are brand-new flows with no existing Power Automate GUID — import `HD24.zip`/`HD25.zip`/`HD26.zip` from `flows/` with **Create as new** (never Update, which needs an existing flow to target), the same way HD23 was imported when it first shipped. ## Reply to a closed ticket

If someone replies — by email or in the Teams chat — to a ticket that's already Closed, the system doesn't reopen it. It starts a **new ticket** instead, tagged "Follow-up to IT-<old number>" in Details, and (via Teams) titled "Follow-up: <old title>" with the same Category/Priority carried over. If the old ticket had a resolution on file, it's copied into the new ticket's Details too ("Previous resolution (IT-<old number>): ..."), so you can see what was already tried without flipping back to the old ticket. The old ticket stays closed as the record of what was done; work the new one like any other.

## Flow reference

HD1 Email intake · HD2 Form intake · HD3 Ticket created · HD4 Ticket updated · HD5 Planner task completed · HD6 Clock · HD7 My open tickets · HD8 Daily report · HD9 Card actions · HD11 Tech thread replies · HD12 Requester replies in Teams · HD13 One-time setup of the pending-replies list · HD14 Teams app intake · HD15 Dashboard stats · HD16 Health check · HD17 Fix ticket permissions (run once) · HD18 Quick close (SharePoint) — the list button's flow; its ID goes into `dashboard/tickets-id-column.json` (`HD18_FLOW_ID`) · HD19 Project created · HD20 Project updated · HD21 No-update check (daily, 9am, repeats until the project is updated) — see "IT Projects" above · HD22 Fix project permissions (run once) — HD17's twin for IT Projects · HD23 Monthly report (1st of the month, 9am) — see "Clock, reports and reminders" above · HD24 Project task created · HD25 Project task updated · HD26 Project task overdue check (daily, 9:15am, repeats until the task is completed) — see "Project tasks" above.

*Flows are generated from `generator/gen.py`. Never edit the live flows directly without updating the generator.*

Every flow also carries a one-line "what this does" summary in its own **Description** field (`FLOW_DESCRIPTIONS` in `generator/gen.py`, set 2026-10-26) — visible on the flow's Details page in Power Automate, in the My flows list, and when importing its zip, so the flow (or a zip sitting on OneDrive) is self-describing without having to open `gen.py` or come back here. For HD18 this field doubles as the on-screen instructions on SharePoint's "Run flow" confirm panel (it has no adaptive-card UI of its own); for every other flow it's just the summary. Add new flows to this dict too — a flow with no entry silently imports with a blank description instead of erroring.
