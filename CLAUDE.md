# Working rules for this repo

- **Read the matching .md before changing anything.** The guides are the source of truth: `app/HD14-app-build-guide.md` for the Power Apps canvas app, `flows/` and `docs/IT-Tech-Guide.md` for the Power Automate flows, `docs/End-User-Guide.md` for what users are told. If the live app or flow disagrees with the guide, say so before changing either.
- **Update the guide in the same change.** Any edit to the app, a flow, the category list, or the notifications must land in the relevant .md in the same commit.
- Don't replace a documented formula with a "simpler" one (e.g. `ddCategory.Default` must stay the live keyword formula in `app/ddCategory-Default.fx`).
- Category names must match in three places: the Tickets list choice column, `ddCategory.Items`, and `generator/gen.py`.
- The dashboard's health panel formatting lives in `dashboard/health-view.json` (ticket systems, DASH row 14) and `dashboard/project-health-view.json` (project systems, DASH row 16); change it there and paste into the matching SharePoint view (*Chart - Health* / *Chart - ProjHealth*), never only in SharePoint.
- Power Automate expressions: never `createArray()` with no arguments (use `json('[]')`); never trust `result('Scope')` for nested steps — list leaf actions in `self_check(..., leaf=...)`; never `substring(x,0,…)` on a string that can be empty (`substring('',0,0)` throws "start index must be less than the length") — pad it first: `substring(concat(x,' '),0,min(length(x),N))`.
- **Power Automate caps `If`/`Switch`/`Foreach` nesting at 8 levels on import** (`"...exceeds the maximum nesting limit of '8'"`, naming the deepest leaf actions) — but a `Scope` action (e.g. `support_msg`'s message-posting wrapper) does **not** add a level, only `If`/`Switch`/`Foreach` do, so count branch-vs-branch nesting by those three types only, not by the JSON's literal object depth. Before adding a new `If` anywhere inside `gen.py`'s deeper flows (HD1, HD12), check what's already nested under the branch you're extending — several paths (e.g. HD12's not-found→closed-ticket→open-tickets chain) already sit at the cap, so one more nested `If` on that path will fail import even though the diff looks small. Prefer collapsing two new conditions into one `If` (put the extra branching only on the shallow/true side) over adding them in series.
- A SharePoint "For a selected item" trigger's `schema` must be the wrapped shape Power Automate's own designer canonicalizes it to — top-level `{"type":"object","properties":{"rows":{...}},"required":["rows"]}`, with an `entity` (row ID) property alongside the dynamic input(s) under `items.properties` — or the SharePoint column-button "Run flow" panel renders no input box at all. If unsure what the canonical shape is, touch an unrelated field in the designer and re-save; Power Automate rewrites the trigger JSON into the shape it expects.
- Never create a SharePoint column with `Hidden="TRUE"` in its schema XML if a flow needs to reference it — SharePoint will neither un-hide (`Cannot change Hidden attribute for this field`) nor delete (`You cannot delete a hidden column`) it afterward via REST, stranding the GUID forever, and Power Automate's SharePoint connector excludes hidden fields from an action's parameter list entirely, which fails package import with `WorkflowOperationParametersExtraParameter`. Use `ShowInDisplayForm`/`ShowInEditForm`/`ShowInNewForm`/`ShowInViewForms` all `"FALSE"` instead to keep a field off forms and views while staying a normal (non-hidden) field. If a new column's name was already taken by a stranded hidden field, SharePoint auto-suffixes the new one (e.g. `NotifiedAttachments` → `NotifiedAttachments0`) — check the real `InternalName` after creating, don't assume it matches what you asked for. **This `ShowInEditForm="FALSE" ShowInNewForm="FALSE"` part of the convention only holds for a field that's never referenced by a `[$FieldName]` token in Header/Body/Footer form-layout JSON formatting (only read/written by flows via `GetItem`/`PatchItem`).** A field with `ShowInEditForm` or `ShowInNewForm` `FALSE` is excluded from the modern list form's entire field set — not just the Edit/New forms, but "Edit columns in the form" (the item panel's "⋮" menu) and every `[$FieldName]` token on Header/Body/Footer too, regardless of `ShowInDisplayForm`. The field also has to be **checked** in "Edit columns in the form" for `[$FieldName]` to resolve anywhere, including in Footer JSON — unchecking it there removes it from the formatting context too, it doesn't just hide the native row. No way was found to make a field's value available to Header/Body/Footer formatting *without* it also rendering as a plain native row wherever "Edit columns" has it checked, so if a field's value needs to show through form-layout formatting (e.g. IT Projects' `TaskDetails`, see "Full per-task details on the project item" in `docs/IT-Tech-Guide.md`), the working pattern is: leave `ShowInEditForm` `TRUE`, leave it checked in "Edit columns in the form" (native row shows, labeled and styled like any other field), and don't also give it a custom Header/Body/Footer formula — pick one rendering, not both, or they duplicate. **`ShowInNewForm` is a separate knob, not a package deal with `ShowInEditForm`** — it only controls whether the field shows (as a blank editable box) on that list's **New-item** creation form specifically, which has nothing to do with Edit-columns/Footer-token availability. Leaving `ShowInNewForm="TRUE"` on a field that makes no sense on a brand-new item (e.g. `TaskDetails` on a project that doesn't have any tasks yet) puts a nonsensical blank box on the New form — caught 2026-10-29 only by a full-circle test after the fix had already shipped. Set `ShowInNewForm="FALSE"` independently whenever the field shouldn't appear on item creation, regardless of what `ShowInEditForm` is set to.
- After adding or changing a SharePoint column that an existing flow's SharePoint action will reference, the connector's cached schema for that list won't show it until something forces a refresh: open the action in the flow designer, reselect the list from the List Name dropdown (even to the same list), and the "Advanced parameters" count will jump up once the refresh lands — only then will package import accept the new field. **The refresh must happen in a freshly-loaded designer tab** (navigate to the flow fresh, don't reuse a designer session that's been open since before the column existed) — repeatedly reselecting List Name in an already-open session can keep showing a stale count (seen stuck at 28 of 28 missing the new field) even though the field is really there. After reselecting, click "Show all" and check the field's display name actually appears in the list, not just that the count went up — a column whose Title collides with an old stranded hidden field (e.g. both titled "NotifiedAttachments") will only show once, under the live one, since the hidden one stays excluded. Note that reselecting List Name, even back to the same list, marks the flow as changed — don't Save; navigate away and let the browser's "Leave site?" dialog discard it (confirms nothing was actually saved).
- Adding a card to a dashboard health panel that uses new `Slot n`/`Share n` columns needs a third step beyond updating `dashboard/health-view.json` and pasting it into the view's *Format current view* JSON: the view's **ViewFields** collection (a separate list of which columns SharePoint actually fetches for that view) must also list the new fields, or the JSON formatter's `[$ShareN]`/`[$SlotN]` tokens silently render as empty/undefined — no error, just a blank grey badge and no description text — even though the `CustomFormatter` JSON and the underlying list data are both confirmed correct. Check with `GET .../views(guid'<view-id>')/ViewFields?$select=Items`; a stale view can be missing a field that's genuinely new (and can also carry legacy leftovers from an earlier card-numbering scheme, e.g. `Slot8`/`Slot9`/`Slot10` already registered from before the current `Slot n+14` convention — don't assume a field being present means it's the one you just added). Fix with `POST .../views(guid'<view-id>')/ViewFields/addviewfield('<FieldName>')`, using an `X-RequestDigest` header from `POST _api/contextinfo`. Found 2026-10-27 shipping HD16's 8th card (Reauthentication, `Share8`/`Slot23`): the card showed correctly in REST and in the generated JSON but not on the live page until both fields were explicitly added to the *Chart - Health* view's ViewFields.
- **"Full circle test" means the whole lifecycle, not just the diff.** When live-testing a change by driving a test ticket through its states, don't stop at verifying the one notification the change touched — a ticket's creation alone fires HD3 end to end (Planner task, confirmation email/chat, channel post, permissions), and the flows run far more leaf actions than the one you're changing. Before declaring a live test clean, check the health self-check output (or, if none was triggered, the actual run history) for **every** flow the test ticket passed through, not only the flow whose code changed — a bug in an untouched flow is just as real as one in the diff, and the only way to catch it is to look. Found 2026-10-25 after shipping an HD4 change, testing it by creating tickets with no `Details` field, and only checking HD4's own notifications each time — missing an unrelated pre-existing `substring('',0,0)` crash in HD3's `Card` action (see the troubleshooting table in `docs/IT-Tech-Guide.md`) that had almost certainly been failing silently on every one of those same test tickets.
